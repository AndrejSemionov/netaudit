## Проблема и границы

`collect_nginx_config()`, `collect_nginx_config_v2()` и `collect_ssh_config()` вызывают `which <tool> || echo NONE` и проверяют наличие строки `NONE`. Сбой `which`, отсутствие самого `which` и отсутствие инструмента дают один результат. При `PATH` обычного SSH-пользователя без `/usr/sbin` установленный `nginx`/`sshd` также может выглядеть отсутствующим, хотя `sudo` с `secure_path` мог бы запустить его.

В scope A1: три коллектора, их потребители (`audit_nginx`, nginx hardening/logs, SSH hardening), существующие тестовые фикстуры, новые RED-сценарии и документация. Прочие `command -v`-проверки исследуются в A2: локально Bash возвращает 1, dash — 127 при отсутствии инструмента (`.ai/FINDINGS.md`). Общий рефакторинг 37 проверок здесь не выполняется.

## Контракт обнаружения

1. Один общий pure-in-result helper в `ssh_utils` возвращает `PRESENT`, `ABSENT` или `UNKNOWN` и диагностическую причину. Он выполняет `command -v <фиксированное имя>` через `run_command_with_exit_code()` с `PATH`, к которому *перед* пользовательским значением добавлены `/usr/sbin:/sbin`. Имена здесь константы `nginx`/`sshd`, а не ввод пользователя. Команда не требует sudo.
2. Код 0 и непустой вывод означают `PRESENT`. Ненулевой код 1 или 127 с пустым выводом означает `ABSENT` для поддерживаемых `/bin/bash` и `/bin/sh`. Нет completion marker, код вне этих значений или код 0 с пустым выводом означает `UNKNOWN`. `UNKNOWN` не превращается в «не установлено» и не даёт оценку безопасности.
3. Найденный через пользовательский `PATH` путь **не** передаётся в sudo: иначе исполняемый файл из каталога, управляемого SSH-пользователем, мог бы выполниться от root. После `PRESENT` прежний `run_sudo_with_exit_code(['nginx','-T'])` / `['sshd','-T']` оставляет выбор бинарника `sudo` и его `secure_path`. Версия (`nginx -v`, `sshd -V`) запускается без sudo с тем же дополненным `PATH`; её сбой не подменяет результат проверки конфигурации.
4. У `NginxConfig`/`NginxConfigV2` поле `installed` становится `True` (подтверждено), `False` (подтверждено отсутствие) или `None` (неизвестно). `SSHConfig` получает эквивалентное поле; версия больше не используется как признак установки. Все потребители явно различают `is False` и `is None`; при `UNKNOWN` возвращают диагностику/ручную проверку, без false PASS или `installed=False`.
5. Если `command -v` подтвердил наличие, но sudo-вызов отказал/завершился ошибкой, сохраняется существующая диагностика sudo/команды. Если два nginx-коллектора расходятся, hardening остаётся без общего балла, как сейчас.

## RED → GREEN и проверка

- RED: fake SSH для трёх коллекторов — 0+путь, 1 и 127 без вывода, отсутствие completion marker, неожиданный код, 0+пустой вывод. При неизвестном статусе все вызывающие проверки показывают ошибку/ручную проверку, не `installed=False`.
- RED: local-shell helper с Bash и `/bin/sh`: отсутствие даёт соответственно 1/127; исполняемый файл в дополнительном системном каталоге находится при урезанном пользовательском PATH.
- RED: найденный путь из управляемого пользователем каталога не подставляется в sudo argv; используются только литералы `nginx`/`sshd`.
- GREEN: реализация helper, три коллектора и потребители; обновление старых fake-ответов с `which` на новый протокол без ослабления утверждений.
- Проверка: targeted pytest коллекции nginx/SSH и интеграции, полный pytest в доступной среде, Ruff, bandit, CI 3.11–3.13. Web TestClient в среде Codex ранее зависал; ограничение отдельно фиксировать, а не считать эти тесты прошедшими.
