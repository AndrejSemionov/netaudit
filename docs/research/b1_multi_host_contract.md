## 2. Граница и единица B2

Рекомендуется **расширить существующую форму `instances`**, не вводить второй
движок отчётов. «Host» для B2 — значение параметра `host` SSH/server checks;
`url`, `target`, `domain`, `hostname`, `server` остаются своими пространствами
идентичности. B2 не объединяет их по совпадающему тексту. Никаких новых
аудитных checks и миграции старых отчётов.

Один запуск B2 может выбирать N сохранённых hosts и набор совместимых с
`host` checks. У каждого check есть ровно один экземпляр на выбранный host,
если оператор явно не сузил список. Ключ в `by_host` создаётся как сегодня,
одинаково в `execution_context` и `timing`; порядок завершения потоков не
меняет отображаемый порядок входного списка. Дубликат host должен быть либо
отклонён до запуска с понятным сообщением, либо иметь явный instance id;
для минимального B2 рекомендуем отклонять дубликат в новом групповом CLI/UI
сценарии, сохранив старое API-поведение `#2`.

## 3. Проект внешнего контракта B2

### 3.1 Выбор hosts и учётные данные

Инвентарь хранит только `id`, `label`, `host`, `user`, `port`, `key_path`.
`password`/`sudo_password` **не хранить** ни в таблице, ни в preset, ни в
`execution_context`, ни в новом summary. `key_path` — локальный путь, не
содержимое ключа; проверять доступность при запуске. Ошибка чтения ключа
возвращает только безопасную причину и не включает содержимое файла или
секрет из исключения. Два разных record id
могут описывать один host с разными `user`/`port`, но групповой запуск одного
check с одинаковым `host` отклоняет такую неоднозначность до выполнения.
Историческая identity остаётся `('host', value)` без user/port — её нельзя
менять без отдельного контракта на тренды.

Групповой CLI: отдельная явная форма `netaudit run <checks...> --hosts-file
<path>` с JSON-массивом записей `[{"host":"...","user":"...","port":22,
"key_path":"..."}]`; файл не содержит паролей. Опциональные общие CLI-флаги
для SSH-параметров применяются ко всем hosts, но конкретные поля записи
имеют приоритет. Секреты — только интерактивный prompt (`--password -`,
`--sudo_password -`) и только в памяти процесса; Web запрашивает их при
запуске. Первая итерация не предлагает разные пароли для каждого host:
если они нужны, оператор запускает группы отдельно. Старый `netaudit run
... --host H` и Web `instances` остаются совместимыми.
В новой форме повтор одного и того же `--host` отклоняется с подсказкой
использовать `--hosts-file`; существующая молчаливая перезапись повторного
`--host` в старом CLI не должна переходить в групповой сценарий.

Новый API инвентаря должен валидировать адрес/user/port/path и возвращать
только перечисленные поля. Существующие `/api/targets` и `/api/presets`
сохраняют прежние форматы; таблицу `targets` с её `kind` не превращать
неявно в SSH-инвентарь. Обязательный серверный тест: попытка передать
`password`/`sudo_password` в payload инвентаря отклоняется, сохранённые
строки SQLite и GET-ответ не содержат тестовый секрет. Следовать уже
существующему `SECRET_PARAM_NAMES` и последнему барьеру storage.

### 3.2 Параллельность и таймауты

Один лимит активных экземпляров на запуск Web/CLI, начальное значение
**4**, допустимый диапазон **1–16**. В одном Web-процессе дополнительно
действует общий предел **8** активных экземпляров от всех одновременных
запусков: несколько HTTP-запросов не обходят ограничение одного запуска.
В Web фактический максимум одного запуска — `min(лимит запуска, свободные
места общего лимита 8)`: выбранные 9–16 не означают столько одновременных
workers в этом процессе. Общая очередь ожидающих запросов обслуживается
FIFO с выдачей одного свободного слота за ход и возвратом запроса в конец
очереди, если у него остались hosts; большой запуск не вытесняет остальные.
Очередь не создаёт поток на каждого ожидающего host. Лимит относится к
`run_instances()` и обоим вызывающим путям (`run_checks_multi`,
`run_stream`). `timing.decide_mode()` и
`_per_check_estimate()` считают не `max`, а оценку по ограниченным группам;
это лишь оценка, не SLA. Ошибка одного host не останавливает остальные.
Неограниченный ввод (в том числе прямой `/api/run`, `/api/stream/start`)
отклоняется до запуска: рекомендуемый максимум **64 instances на check**
и **256 суммарно на запрос**.

Различать три времени: (1) ожидание в очереди; (2) SSH connect/command
timeout; (3) общее время проверки одного host. Сегодня действует только
(2), причём как таймаут отдельной операции. Python worker thread нельзя
безопасно принудительно убить. `future.result(timeout=...)` вернёт управление
ожидающему, но оставит проверку и возможные побочные действия работать в
фоне; это **не** допустимый «таймаут host». Для минимального B2 рекомендуем
вариант A из §5: существующие SSH timeouts без общего срока. Вариант B —
общий срок в `SSHExecutor`: сторожевой таймер закрывает client/transport,
а прерванный или следующий `run()` выбрасывает исключение, которое engine
записывает как `error` экземпляра, не выдавая пустой/частичный stdout за
чистый результат. По исходникам Paramiko закрытие канала будит поток,
ожидающий `read()`, но достаточность этого при всех точках блокировки —
**HYPOTHESIS** до RED-теста с fake transport или локальным Paramiko server.
Даже при подтверждении это не строгий wall-clock deadline произвольной
локальной работы Python. Вариант C — subprocess с принудительным завершением
локального процесса для более строгого wall-clock предела; ему нужен
отдельный контракт. В обоих вариантах B/C удалённая команда после закрытия
SSH-канала может продолжить работу на сервере; прекращение процесса клиента
не гарантирует отмену её побочных действий. `ThreadPoolExecutor` сам по
себе не решает ни одну из этих задач.

Потеря ключей `known_hosts` уже возможна в Web `instances` на текущем
`main`. Её исправление нужно отдельным решением USER: отдельная задача
сейчас (**рекомендуется**, так как дефект уже существует) или шаг 0 B2,
обязательный до включения новых входов B2. Требование к исправлению:
атомарное сохранение с межпроцессной блокировкой и повторной
проверкой уже записанного ключа под этой блокировкой. Если другой worker
сохранил для того же host иной ключ, соединение отклоняется, а не
перезаписывает trust. Не удерживать блокировку во время сетевого connect.
Отдельный тест с двумя конкурирующими первыми подключениями подтверждает,
что оба ключа сохранены; тест конфликта одного host подтверждает отказ.

### 3.3 Отчёт, сводка, сравнение

Старые поля отчёта и ответы `/api/run`, SSE, `history`, `trend` не меняются.
Сводка B2 вычисляется при чтении одного сохранённого отчёта из
`results` + `execution_context`, не дублируется в SQLite. Одна строка на
`host`: `completed_checks`, `errored_checks`, наблюдённые количества
`critical/high/medium/low`, список checks с `error` и ссылкой на подробный
результат. Ошибка и недостаточный сбор данных отображаются отдельно от нуля
findings; ноль наблюдённых проблем не называется «хост безопасен».
Формы findings читать через общий helper `trends._scoped_findings()` (или
вынесенный из него общий helper): он понимает плоский `findings`, вложенные
`server_audit.sections[*].findings` и разделы-списки `dns_audit`, не считая
один finding дважды. Недостаточный сбор — `error`, либо finding с
`requires_manual_verification` при любой severity, либо непустой
`warnings`. Для неизвестной формы выводить «нет сопоставимых findings»,
не ноль. Сравнение hosts показывает строки одной **и той же проверки**
одного запуска, её статус и наблюдённые severity counts; не вычитает
findings разных checks и не объявляет отсутствующий ID исправленным.
Дубликаты и имя host в результате берутся из `execution_context` params,
а не из суффикса `by_host`.

## 4. Порядок реализации и приёмка B2 после утверждения USER

0. По отдельному решению USER закрыть уже существующую потерю SSH trust
   из §3.2: самостоятельная задача до B2 (рекомендация) или обязательный
   первый шаг B2. До её проверки новые входы B2 не включать. Два теста:
   первые ключи разных hosts оба сохраняются; другой ключ того же host
   отклоняется. Старый Web-путь тоже должен получить исправление.
1. Контрактные тесты формата и секретов; CLI parser RED; ограничение
   concurrency RED с измерением одновременно активных экземпляров.
2. Общий bounded dispatcher в `engine.run_instances()`; оба вызывающих
   пути используют его. В ответах для одного экземпляра сохраняется flat
   форма, для N>1 — прежняя `by_host`; failure одного host не теряет другие.
   Проверить пределы 4/8 и честное ожидание между запросами из §3.2.
3. Инвентарь без секретов и CLI/Web выбор hosts; прямые API-входы проверяют
   лимиты; старые targets/presets и одиночный CLI остаются рабочими.
4. Read-only summary/сравнение. Тесты на mixed success/error, неизвестную
   форму, секреты, дубликат host и стабильный порядок.
5. E2E на существующем GitHub Actions SSH-стенде: минимум два hosts (или
   два изолированных sshd endpoints), один успешен, другой даёт отказ или
   timeout SSH-операции; успешный результат и точная ошибка обе сохранены;
   проверка отсутствия тестового пароля в JSON/SQLite/SSE/log/AI. Полный
   pytest, Ruff, bandit, pip-audit и CI.

Без утверждения USER B2 не начинать. B1 завершается согласованным
документом; ни один пункт выше сам по себе не разрешает реализацию.

## 5. Вопрос на утверждение USER

**Срок проверки одного host — выбор USER для B2:**

| Вариант | Что обещаем | Цена и предел |
| --- | --- | --- |
| A — существующие SSH timeouts (рекомендация для минимального B2) | Ограничены отдельные connect/command операции; общего срока нет | Меньше изменений; зависший host может задержать группу |
| B — срок внутри `SSHExecutor` (HYPOTHESIS) | По истечении срока закрыть client/transport; `run()` выдаёт ошибку вместо частичного/пустого ответа, engine сохраняет `error` экземпляра | Нужен RED-тест разблокировки `read()` и всех применимых SSH-путей. Локальная работа Python после SSH не имеет строгого wall-clock предела; удалённая команда может продолжаться |
| C — subprocess на host | Родитель принудительно завершает локальный процесс по общему сроку и записывает ошибку host | Отдельная архитектура и контракт до B2; удалённая команда может продолжаться после закрытия соединения |

Рекомендуем A для минимального B2, поскольку существующий контракт не
обещает общего срока. Если USER нужен наблюдаемый срок для SSH-пути без
строгой гарантии всей проверки — исследовать B отдельными RED-тестами до
утверждения его реализации. Если нужен контролируемый предел для локального
worker целиком — C. Ни B, ни C не гарантируют прекращение удалённой команды
и её побочных действий.

**Отдельное решение USER по `known_hosts`:** исправить воспроизведённый
дефект сейчас отдельной задачей (рекомендуется, так как Web уже уязвим к
потере trust) или сделать обязательным шагом 0 B2. B1 только документирует
это решение; исправления `ssh.py` в данном PR нет.
